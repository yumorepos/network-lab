# AGENTS.md: working rules for coding agents

Instructions for any coding agent working in this repository. Derived from
`CLAUDE.md`, which remains in force and is the original. The two files state the
same substantive rules; where wording differs, `CLAUDE.md` is authoritative.

Read `docs/CODEX_HANDOFF.md` first for current state, then this file for the
rules, then `PHASE_5_6_PLAN.md` before implementing anything new.

## 1. What this project is

Network Lab is a route-evaluation engine for airline network planning, built
entirely on open government data. One config-driven pipeline turns raw BTS,
StatCan, BEA and EIA files into LAUNCH / MONITOR / PASS verdicts for new airline
routes. A study is a YAML file in `config/studies/`, not a code change.

Three studies run through the same engine: WestJet YYC (flagship, transborder),
Alaska SEA (validation, US domestic, where demand and share are observable) and
Porter YYZ (portability, transborder).

The build is complete and shipped. Current work is Phase 5 and Phase 6, whose
purpose is to replace asserted parameters with measured ones.

## 3. Architecture orientation

```
ingest/     one client per source -> data/raw/ (gitignored), typed Parquet
warehouse/  DuckDB marts: dim_airport/carrier/metro, fact_segment (T-100),
            fact_od_market (DB1B), fact_costs (Form 41), fact_fuel (EIA);
            reconcile.py checks computed totals against published ones;
            route_spells.py derives the mechanical route-spell register
models/     catchment -> demand -> competition -> QSI-lite share -> spill ->
            economics (3x3 grid) -> screen (fixed-gauge LAUNCH/MONITOR/PASS)
backtest/   score real 2021-2025 launches with a pre-2022 model; post-mortems
reports/    generated markdown business cases and ranked tables
app/        Streamlit dashboard reading only the precomputed outputs
scripts/    check_reproducible.py (the gate), phase6a_compare.py
```

Where things live:

- `config/assumptions.yaml` - every assumption, one file.
- `config/studies/*.yaml` - a study is a config, not a code change.
- `models/screen.py` - the verdict logic and the fixed-menu schedule evaluation.
- `models/gravity.py` - gravity public interface and estimator dispatch.
- `models/gravity_log_ols.py`, `models/gravity_poisson.py` - the two estimators.
- `reports/generate.py`, `backtest/postmortem.py` - report generators.
- `tests/test_sanity.py` - correctness-critical logic and the served-market
  cross-check.
- `tests/test_p0_regressions.py` - one test per audited P0 defect.
- `tests/test_consistency.py` - reader-facing docs and verdict counts must match
  the computed artifacts.
- `tests/test_phase6a_poisson.py` - the Poisson estimator and the baseline freeze.

## 4. Data-grain rules

These are the rules most likely to be violated by an agent moving fast.

1. **T-100 is SEGMENT data. DB1B is O&D data. Never join them as if they share a
   grain.** T-100 counts who flew the metal on one airport pair; DB1B counts
   where a ticket started and ended.
2. **T-100 has no Canadian domestic segments.** They never touch the US, so they
   are not reported to BTS. This is why Air Canada connecting itineraries out of
   Canadian hubs are structurally invisible (LIMITATIONS item 14), and it is a
   legal consequence of Canada's disclosure regime, not a coverage gap that
   better querying can close.
3. **T-100 reports the operating certificate. A passenger buys a marketing
   brand.** SkyWest, Republic, Envoy and Horizon never appear as a DB1B
   ticketing carrier. Resolve certificate to brand through `models/carriers.py`
   and `data/reference/carrier_families.csv` before treating a carrier as a
   competitor or as an incumbent.
4. **Demand is bidirectional. Frequency is one-way.** `demand_pax_yr` counts A
   to B plus B to A; `freq_wk` counts one-way departures from the hub. Annual
   departures are `freq_wk * 52 * 2`. Getting this wrong scored every route at
   twice its true load and survived four review passes.
5. **Money is USD internally. Distance is converted once, on ingest.**
6. **Demand provenance is recorded, always.** Demand is observed (DB1B) where it
   exists, anchor-scaled or gravity-plus-transfer only where it does not. Every
   demand row records which path produced it via `demand_source` and
   `demand_method`.
7. **Never invent a column name.** Read the record layout in `data/reference/`
   or the mart definitions in `warehouse/` first.

## 5. Assumption rules

1. **Never invent a numeric constant.** Every non-derived value lives in
   `config/assumptions.yaml` with source, confidence and sensitivity.
2. **A missing value is a question, not a default.** Stop and ask. No plausible
   industry defaults.
3. Every constant added, removed, fitted or moved into `assumptions.yaml` is
   listed in section 5 of the change report.
4. Known outstanding violations are catalogued in
   `AUDIT_2026-07-27_VERIFIED.md` section 6.1 and are tracked roadmap work, not
   licence to add more.

## 6. Generated-output rules

1. **Reader-facing numbers and verdict counts are read from computed artifacts,
   never hardcoded.**
2. **Never hand-edit generated markdown.** Everything under `reports/`, plus
   `docs/validation.md` and `docs/backtest.md`, is generated. Fix the generator
   in `reports/generate.py`, `backtest/postmortem.py` or `models/run_all.py`.
3. Regenerate with `make reports` (or `make all`).
4. **Never commit anything under `data/` except `data/reference/`.** The
   Streamlit deploy force-adds `data/parquet/outputs/` explicitly; see
   `docs/deploy.md` and the `deploy-prep` make target.
5. **No em dashes, en dashes or double hyphens** in any generated text, comment
   or document. Spaced hyphens only.

## 7. Test discipline

1. **If a test fails, report the failing values.** Never relax an assertion,
   widen a tolerance, or edit an expected value to make a test pass.
2. **A test that has never been shown to fail is a test of nothing.** When you
   add a regression test, demonstrate that it fails when the defect is present,
   and record that you did. This is the explicit lesson of round 4.
3. Consistency testing is not correctness testing. The three P0 defects in round
   4 all passed a full green suite.
4. Tightening a guard, or widening what it covers, is not the same as relaxing
   one and is always allowed.
5. **Byte equality of Parquet is not a reproducibility contract.** Float
   last-bit noise and Parquet metadata change the bytes while the content is
   identical. The contract is the content comparison in
   `scripts/check_reproducible.py`, which joins on keys and tolerates 1e-6.

## 8. Model-change discipline

**Every change in Phase 5 and Phase 6 ships with a before-and-after report.** A
change without one does not merge. This applies to changes that make things
worse, which are reported rather than reverted silently. Template:
`docs/change_report_template.md`. Filed reports: `docs/change_reports/`.

The report carries four fields:

1. **Metric impact.** The affected metric before and after, on the frozen W1.4
   baseline where applicable.
2. **Verdict changes.** Per study, the LAUNCH, MONITOR and PASS counts before
   and after, and **every market that moved between categories, by name**.
   Counts alone hide compensating moves.
3. **Regression risk.** Which existing tests guard this change, and what class
   of error would still slip through.
4. **Statistical meaningfulness.** An interval, a holdout comparison, or an
   explicit statement that the sample is too small to say. "The number moved in
   the right direction" is not an acceptable answer on its own.

### The frozen baseline

`docs/W1.4_baseline_freeze.md` freezes the Version 1 baseline at commit
`bd7d4dd`. **Every Phase 6 change is measured against it and cites it by commit
hash.**

Three rules follow:

- **Do not change a model default as a side effect of landing code.** Moving a
  default is its own evidence-gated decision with its own change report and a
  new baseline freeze. `tests/test_phase6a_poisson.py` asserts the current
  default and will fail if it moves.
- **Do not let the baseline drift while it is being built.** A baseline that
  moved while it was being measured is not a baseline.
- The freeze is an **artifact** baseline, not a **predictive-skill** baseline.
  The W1.4 decision replay is not implemented, so no change can currently claim
  improved predictive skill on real launches. Do not claim it.

## 9. Git safety

- No destructive operations. No `git reset --hard`. No force push.
- Do not rewrite or squash existing history.
- Do not delete untracked or modified files until their provenance is
  understood. Running `make all` legitimately rewrites tracked Parquet with
  float last-bit noise; verify the content is unchanged before restoring.
- Commit or push only when asked. If on the default branch, branch first.
- Current work branches from `main`; the active branch is
  `phase5/milestone-a-integrity`.

## 10. Commands to run before declaring work complete

The definition of done. All of it, from a clean state.

```bash
make all          # models + backtest + reports        (~3 min)
make test         # sanity, P0 regressions, consistency (~1 min)
make reproducibility  # warehouse rebuild + content diff (~6 min)
```

Expected as of this writing: `make test` 45 passed, `make reproducibility`
27 artifacts identical.

Then confirm:

- new constants are in `assumptions.yaml` with a source;
- reports are regenerated from outputs, not hand-edited;
- the consistency tests pass, since they fail the build if any headline number
  or verdict count drifts;
- `PROGRESS.md` reflects the current numbers;
- the change report is filed in `docs/change_reports/`;
- `git status` is clean, or the only differences are float noise you have
  verified as immaterial.

`make data` re-downloads every source and rebuilds the warehouse. It takes about
50 minutes cold and is not needed for model work; the warehouse is already
built.

## 11. Before implementing future work

**Read `PHASE_5_6_PLAN.md` first.** It carries the approved scope, the
sequencing, and the reasons for it. In particular:

- **Phase 5 measures. Phase 6 changes.** Nothing in Phase 6 starts before the
  W1.4 baseline exists.
- **Every ingestion task must retire a named assumption or validate a named
  output.** No task exists to raise the source count.
- Milestone C (ADS-B) is a design note only, unless a trigger in W4 fires.
- The out-of-scope list at the end of the plan is deliberate. Continuous DB1B
  history, ADS-B implementation and the README rewrite are all excluded on
  purpose.

Do not reorder the plan silently. If the evidence says the order is wrong, say
so in writing and propose the change before acting on it.
